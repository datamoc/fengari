Pourquoi notre interface JavaScript ↔ Lua ?

Nous voulons que Lua manipule les données d’une application et appelle les opérations que celle-ci lui confie. L’hôte garde la maîtrise de ses objets et de l’exécution.

PyroeisVm fournit donc une interface d’échange intégrée au moteur. Ce choix répond aux besoins des règles de jeu, des stratégies et des scripts intégrés dans une application. Il explique pourquoi nous n’utilisons pas directement fengari-interop.

Essayer les échanges dans les deux sens : données, callbacks JavaScript, retours multiples et références à des fonctions Lua.

Des données copiées et des opérations explicites

Un objet JavaScript ordinaire transmis à Lua devient une table construite à partir de ses propriétés propres énumérables. Un tableau devient une table indexée à partir de 1. Lua peut modifier ces tables sans modifier automatiquement les objets JavaScript d’origine. Leurs prototypes ne sont pas exposés par cette conversion.

Dans l’autre sens, les tables Lua deviennent des tableaux, des objets ou des Map JavaScript suivant leurs clés. Ce sont des instantanés de leurs données : leurs métatables et leur comportement ne sont pas transportés. Les appels utilisent run, call et les fonctions enregistrées avec defineFunction.

const { PyroeisVm } = require('@datamoc/pyroeis');
const vm = new PyroeisVm(undefined, undefined, {
  sandbox: true,
  limits: { instructions: 30000, timeMs: 50 }
});

vm.run(`
  function choose(targets)
    local best = 1
    for i, target in ipairs(targets) do
      if target.distance < targets[best].distance then best = i end
    end
    targets[best].distance = 0 -- modifie seulement la table Lua
    return best
  end
`);

const targets = [{ distance: 8 }, { distance: 3 }];
const selected = vm.call('choose', targets); // 2 (indice Lua)
console.log(targets[1].distance);            // 3, objet JS inchangé
if (!Number.isInteger(selected) || selected < 1 || selected > targets.length) {
  throw new Error('Invalid target index');
}
const target = targets[selected - 1];        // l’hôte valide et applique

C’est le modèle de la démo MWG : le moteur de jeu conserve sa carte, son pathfinder et ses objets de rendu. Il envoie des descriptions de cibles au worker Lua et reçoit un indice validé. Le script ne reçoit aucun objet du moteur de jeu par référence.

Lorsqu’un script doit agir sur l’hôte, nous exposons une opération précise :

vm.defineFunction('game.log', message => {
  if (typeof message !== 'string' || message.length > 200) {
    throw new Error('Expected a message of at most 200 characters');
  }
  console.log(message);
});
vm.run('game.log("Ready")');

Ce callback fournit une seule opération avec validation des arguments. Il n’expose pas automatiquement console, le DOM ou le reste des objets de l’application. Un callback qui renvoie un objet contenant d’autres fonctions élargit toutefois l’interface : les fonctions JavaScript transmises sont converties en fonctions hôtes appelables.

Ce que propose fengari-interop

La bibliothèque amont conserve les objets JavaScript sous forme de userdata et permet de manipuler des valeurs Lua depuis JavaScript via des wrappers. Sa bibliothèque js donne notamment accès à js.global, à la construction d’objets et aux proxies. Elle convient à du Lua de confiance qui travaille directement avec des API JavaScript. Ces comportements sont décrits dans son README et son implémentation.

Nous choisissons l’interface Pyroeis pour rendre les entrées, les résultats et les actions du script explicites. Cela ne constitue pas une affirmation selon laquelle fengari-interop serait intrinsèquement dangereux, ni selon laquelle notre conversion serait toujours plus rapide.

Une interface liée au cycle de vie de la VM

Nous conservons une API commune pour les appels protégés, les erreurs LuaError et LimitError, les coroutines et les budgets. Une fonction Lua lue depuis la VM devient un LuaRef ancré dans son registre ; son appel repasse par la VM. Les threads et les userdata complets utilisent aussi des références. Elles appartiennent à une VM précise, et release() permet de les libérer explicitement. La collecte automatique, lorsqu’elle est disponible, reste une aide sans délai garanti.

Les types d’échange expriment aussi des choix utiles à nos applications : les entiers Lua dépassant la précision sûre de Number sont lus comme BigInt ; une chaîne Lua non UTF-8 est lue comme Uint8Array ; LuaFloat distingue un flottant entier en valeur ; Multi et Yield représentent des retours multiples et une suspension. Userdata permet un passage opaque explicite, sans proxy général ajouté automatiquement.

Les coûts et les limites de ce choix

  • Les copies prennent du temps et de la mémoire. Les grandes structures, les appels fréquents et les objets dont l’identité doit être partagée peuvent justifier un autre adaptateur.
  • Les classes JavaScript, leurs méthodes de prototype et les métatables Lua ne sont pas reproduites par une conversion de données. Il faut concevoir une API pour les comportements nécessaires.
  • La lecture d’une table Lua préserve ses cycles et les tables partagées au sein d’une conversion. La conversion d’un graphe JavaScript vers Lua ne mémorise pas son identité : les références partagées sont recopiées et les cycles finissent par être refusés par la limite de profondeur.
  • null et undefined deviennent tous deux nil. Une entrée de table à laquelle on affecte nil disparaît ; toutes les données JavaScript ne font donc pas un aller-retour sans changement.
  • Un callback JavaScript reste du code hôte de confiance. Un budget Lua ne peut pas préempter une boucle JavaScript arbitraire, annuler ses effets externes ni plafonner toutes ses allocations. Les conversions elles-mêmes peuvent parcourir beaucoup de données ; l’hôte doit borner les entrées et les sorties.
  • sandbox: true ne retire pas les fonctions que vous choisissez d’exposer. Pour du code non fiable, associez une interface restreinte, des budgets, la validation des résultats et une isolation extérieure adaptée, comme le worker de la démo.

Pourquoi ne pas brancher simplement la bibliothèque amont ?

La version 0.1.4 examinée importe fengari et déclare ce paquet comme dépendance pair ^0.1.0 dans son manifest. Pyroeis est un autre paquet et poursuit sa propre implémentation Lua. Changer le nom de l’import ne prouverait pas la compatibilité des états et de l’API C.

Un portage devrait vérifier cette compatibilité, les chemins d’appel, la gestion des références, les conversions numériques et les accès accordés au script. Nous ne fournissons pas aujourd’hui cet adaptateur comme intégration prise en charge. Pour nos usages actuels, l’interface de PyroeisVm fournit directement le contrat que nous voulons maintenir et tester.
